## 0. Correction to the brief

You described this as **63 lessons across 14 modules**. The shipped course is **86 lessons across 19 modules** (`TOTAL_LESSONS = 86`; `src/curriculum/index.js` has 19 module entries; `registry.js` maps 19 payloads). ## 1. Headline

The curriculum is genuinely strong. Teaching order is machine-enforced by `teachingGraph.js` and it works: I could not find a single code-surface concept used before it is taught. Validators are not no-ops — I ran every validator against both its starter and its solution, and **all 83 solutions pass while 82 of 83 starters correctly fail** (the one exception, `reconciliation`, is a deliberate observation-only lesson gated by `requiresObservation`). The mental-models and modern-react modules are better than most paid courses.

The problems are concentrated in four places:

1. **The app is not offline-first.** Sandpack has no `bundlerURL` override, so every playground and every challenge round-trips to `https://2-19-8-sandpack.codesandbox.io/`. The README's first sentence and CLAUDE.md's first line both claim offline-first. The local fallback (`localBundler.js`) exists but is dead code.
2. **The forwardRef contradiction you flagged is still live**, unfixed, and is the single worst factual error in the course.
3. **The React Compiler is described as automatic in React 19** in two lessons, and correctly as opt-in in a third.
4. **Three lessons ship a `solutionCode` with no default export**, so "Reveal Solution" hands the learner code that cannot run.

Counts: **1 Critical, 13 High, 34 Medium, 22 Low.**

> **Status after round two (§11, §13):** all four of the above are fixed, and every proposal in §8 has been applied. The course is now **95 lessons across 21 modules**; the figures in §0 and in the tables below are the numbers as reviewed, not as shipped. Two claims in this review were themselves wrong and are corrected at the top of §13.

## 2. PASS 1 — Code quality & correctness

- **JS before React: excellent.** All eight JS lessons land before JSX, and `teachingGraph.js` proves it mechanically.

## 4. PASS 3 — Pedagogical & factual consistency

The contradiction class you were worried about is real and there are **four distinct clusters**.

### Cluster A — forwardRef (CRITICAL, lesson 47)

`intermediate.js` lesson body, solution and all three learning checks correctly teach React 19: *"ref is a plain prop — no forwardRef wrapper needed."*

Its own misconception card (`intermediate.js:757-775`) says the opposite:

```js
// INCORRECT
function MyInput({ ref }) { return <input ref={ref} />; }
// CORRECT
const MyInput = forwardRef((props, ref) => <input ref={ref} />);
```
> "`ref` and `key` are special reserved words in React. You cannot access them normally through the `props` object." … "you **MUST** wrap the component in `forwardRef`."

The card labels the lesson's own solution as INCORRECT. The `pro-tip` card (`:821-836`) repeats the legacy form. This is the exact failure you described, still present.

### Cluster B — refs during render (High)

Three lessons disagree about whether `ref.current += 1` in the render body is allowed:

| Source | Position |
|---|---|
| 22 `pure-rendering`, pitfall 3 + insight 1 | "the **closer-to-sanctioned** version… React explicitly tolerates refs used this way" — presented as ✅ and as the *fix* for Strict-Mode over-counting |
| 27 `use-ref`, insight 1 | `renderCount.current += 1` shown "Inside component body or event handler" |
| 27 `use-ref`, insight 3 | "**Never** write to `ref.current` during the render phase — breaks Concurrent Mode!" |
| 27 `use-ref`, explain check | "Why does React tell you **not to** read or write `ref.current` during render…" — correct |
| 36 `diagnostic-stale-closure`, insight 1 | `latestCount.current = count; // Sync on every render` at the top level of the body |

The learning check has it right. Worse, lesson 22's claim is **factually wrong**: the ref object persists across Strict Mode's double-invoke, so `renderCount.current += 1` double-counts exactly like the module variable it's offered as a fix for.

### Cluster C — why `class` isn't allowed in JSX (High, lesson 11)

Four voices in one lesson:

| Source | Explanation |
|---|---|
| Lesson body, Rule 2 | DOM property naming convention |
| Solution walkthrough, step 2 | "`class` is a **reserved JavaScript keyword**… The compiler would choke on `class=`" |
| Misconception card, code comment | `// ❌ SyntaxError — 'class' is reserved in JavaScript` |
| Misconception card, step text | "**Do not** model this as a special React ban on the JavaScript keyword" |
| Learning check, transfer model answer | "…className, not class (**which is a reserved word in JavaScript**)" |

The card contradicts its own code comment. And the "SyntaxError" framing is false — `<div class="x" />` parses fine; React 19 emits a runtime warning, not a compile error.

### Cluster D — React Compiler shipping model

Covered in §2.5. Lesson 66 is right; 29 and 50 are wrong.

### Exercise scoping problems

Several challenges cannot demonstrate the bug they describe:

- **37 `diagnostic-missing-cleanup`** — `App({ userId = 1 })` never receives a changing prop in the sandbox, so the race condition is unobservable. The `### Example` version (with a button) is correct; the challenge version isn't.
- **81 `debug-identity`** — `App({ roomId })` never re-renders, so the "Effect fires every render" symptom never appears.
- **40 `use-debounce`** — the stated lag comes from reconciling 10,000 `<li>` on every keystroke. Debouncing the filter string does not reduce that; React still diffs the full list per keystroke because `filter` state changes. The exercise's premise doesn't hold.
- **25 `form-validation`** — the solution disables submit whenever `isInvalid`, which makes `setError(...)` inside `handleSubmit` permanently unreachable. The walkthrough then claims "we combine both real-time validation and post-submit validation" — the second half is dead code.
- **11 `jsx-intro`** — the challenge announces "three JSX errors: a missing root wrapper, a `class` attribute, and an unclosed `<img>`". The starter already has a single root `<div>`. Only two errors exist; hint 1 asks the learner to fix a rule that isn't broken.

## 8. PASS 5 — Expert suggestions (nothing here is "broken")

> **All fifteen have been applied.** See §11 for S5, S8 and S15, and §13 for the rest. **S1 · Make offline-first true, or stop claiming it.**
The honest options are: self-host a Sandpack bundler build alongside the Electron app and set `bundlerURL`; finish the `localBundler.js` path you already started and use it as a fallback when the hosted bundler is unreachable; or remove the claim. **S2 · Add a `ts-fundamentals` module (4–6 lessons) before lesson 68.**

Suggested shape: keep **17 `lists-and-keys`** (mechanics), merge **21 + 49** into one "Identity, keys, and deliberate remounts" lesson, and merge **51 + 81** into one "Reference identity breaks memo *and* Effects" lesson. **S4 · Run `tsc` in a worker for the TypeScript module.**
Bundling `typescript` and calling `ts.createProgram` / `transpileModule` with diagnostics inside a Web Worker would let `ts-diagnostics` show real compiler output against the learner's code — turning the weakest module into the most convincing one. **S5 · Adopt the `runtimeTests` harness you already built.**

You recommend it twice and never teach it. ### S4 — real `tsc` diagnostics, offline

This was the one item I expected to leave as a proposal, and it works.

`src/workers/typecheck.worker.js` runs an actual TypeScript language service against the file in the editor. The compiler, the `ES2020` + `DOM` lib declarations and `@types/react` are all bundled at build time, so it needs no network. Results appear under the playground and under the challenge preview, with real line/column positions and real error codes.

Two things worth knowing about how it is built:

- **It is an inlined blob worker, deliberately.** A packaged build is served over `file://`, where the page origin is `null` and a worker loaded from a `file://` URL is refused by Chromium. A blob URL constructed by the page itself is allowed. I verified the blob-worker path works from a null origin before building on it.
- **It reports, it never blocks.** The playground still runs whatever you wrote, and Check Answer still grades it. That is also the honest model: `tsc` does not stop `vite build` either.

The whole thing is one lazily-loaded 1.4 MB (gzipped) chunk that is only fetched when a TypeScript lesson opens.

Swept every TypeScript lesson through the real compiler afterwards: **all 24 playground and solution surfaces typecheck clean under `strict`**, and every starter reports exactly the errors its challenge asks the learner to fix — `ts7006` implicit any, `ts2339` `toUpperCase` on a number, `ts2345` `SetStateAction<null>`.

### Two more things found while doing the above

- **Orphaned dev playground directories.** Moving a lesson between modules leaves `src/playground/<old-module>/<lesson>/` addressed by a module id that no longer matches, and dev simply stops serving it — silently. Three were orphaned (two from the S9 split, one from a much older move whose file had drifted *and* was mojibake-corrupted). All relocated or removed, and `validate:curriculum` now names any directory that matches no lesson.
- **`keyboard-and-focus` gave away its own answer.** Its playground was the challenge solution verbatim, so opening the lesson handed the reader the fix. Replaced with the other half of the lesson — a `div onClick` next to a real `<button>`, operated by keyboard — which nothing in the challenge covers.
- **A duplicate object key silently deleted three learning checks.** `learningCheckExtensions.js` had `'diagnostic-object-identity'` as a key **twice**. The second entry arrived when `debug-identity` was merged away and its Effect-identity questions were re-keyed onto the surviving lesson — and in a JavaScript object literal the later key wins, so the lesson's original three memo-identity checks stopped existing. Nothing failed: the count was still valid, the checks were just gone. Both sets are now merged into one entry (5 checks), which is coherent for a lesson called "Reference Identity" — the same comparison breaks `memo` and dependency arrays alike. Found by `npm run lint`, which is why it is now worth running.
- **Every module overview page showed the wrong module number.** `ModuleOverview.jsx` rendered `Module {moduleIdx}` straight from a 0-based `findIndex`, so the page said "Module 14" for the module the sidebar and the overview badge both called 15 — for all 21 modules, not just the new ones. This is the failure `index.js`'s own header comment says derived numbering exists to prevent; one code path was doing the derivation off by one. Fixed, and the variable renamed to `moduleNumber` so the next reader cannot make the same mistake.
